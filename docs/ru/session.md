# Сессия

Сессия EPP — это TLS-соединение, поверх которого выполнен вход. Эта страница охватывает всё от
сокета до выхода: настройку клиента, проверку сертификата сервера, открытие и закрытие сессии, смену
пароля, чтение предупреждений безопасности от сервера и запись кадров в журнал без утечки учётных
данных.

Форма её никогда не меняется:

```
connect()  →  <greeting>  →  login()  →  commands …  →  logout()  →  disconnect()
```

`connect()` открывает сокет и читает приветствие. `login()` выполняет аутентификацию. Идут команды.
`logout()` завершает сессию на стороне реестра, а `disconnect()` закрывает сокет.

## Config

`EppTools\Config` хранит настройки соединения. Создайте его конструктором или через
`Config::fromArray()`, который принимает те же имена в качестве ключей и подставляет все значения по
умолчанию:

```php
use EppTools\Config;

$config = Config::fromArray([
    'host'     => 'epp.registry.example',
    'clid'     => 'EXAMPLE',
    'password' => getenv('EPP_PASSWORD'),
    'caFile'   => '/etc/epp/registry-ca.pem',
]);
```

Ключ, который `fromArray()` не распознал, игнорируется, поэтому сверяйте написание с таблицей ниже.
Свойства объявлены публичными, так что всё, что вы не передали, можно прочитать прямо с объекта.

### Все поля

| Поле | По умолчанию | Что это и что будет, если задать неверно |
|---|---|---|
| `host` | `''` | Имя хоста реестра. Пустое вызывает `ConfigException` из `connect()`. Это же значение уходит в TLS как `peer_name` для SNI и проверки имени, поэтому IP-адрес здесь не пройдёт проверку имени против сертификата, выпущенного на имя хоста. |
| `clid` | `''` | Ваш идентификатор регистратора: 3–16 символов из латинских букв, цифр и дефиса. Пустой вызывает `ConfigException` из `login()` ещё до отправки чего бы то ни было. Правильное по форме, но неверное значение сервер отклоняет кодом 2200. |
| `password` | `''` | Ваш EPP-пароль. Пустой вызывает `ConfigException` из `login()`. Короче 6 символов или длиннее 128 — тоже `ConfigException`, ещё до открытия сокета. Длиннее 16 возможен только там, где сервер предлагает RFC 8807, — см. [Длинные пароли](#длинные-пароли) ниже. |
| `port` | `700` | Порт EPP. Меняйте его, только если вам выдали другую точку подключения. Неверный порт даёт `ConnectionException` из `connect()`. |
| `lang` | `'en'` | Язык сообщений о результате от сервера в этой сессии. Реестр объявляет в приветствии `en`, `uk`, `ua` и `ru`; значение, которого он не объявляет, валит вход кодом 2102. Это язык `message()`, а не poll-уведомлений: те несут собственный. |
| `connectTimeout` | `10.0` | Сколько секунд ждать TCP-соединения и рукопожатия TLS. Слишком малое значение на медленном канале даёт `ConnectionException`, который читается как отказ в соединении. |
| `readTimeout` | `30.0` | Сколько секунд ждать кадр ответа. Дробные значения учитываются (`2.5` — две с половиной секунды). Ноль или меньше поднимается до одной секунды, так что «ждать вечно» это никогда не означает. Чтение, вышедшее за тайм-аут, выбрасывает `ConnectionException` и **закрывает соединение**: недочитанный кадр оставляет поток байтов на неизвестном смещении, и следующая команда прочитала бы середину ответа на эту. |
| `verifyPeer` | `true` | Проверять цепочку сертификата сервера. Оставьте включённым. См. [TLS](#tls-и-проверка-сертификата). |
| `verifyPeerName` | `true` | Проверять, что сертификат соответствует `host`. Отключение — узкое послабление (сертификат тот, имя хоста не то), которое иногда оправдано при разработке. |
| `caFile` | `null` | Путь к PEM-связке CA, подписавшего сертификат **сервера**. Обязателен для `epp.registry.example:700`, где используется собственный закрытый CA реестра. Не задан или указан неверно — рукопожатие падает с ошибкой проверки сертификата. |
| `clientCert` | `null` | Путь к **вашему** клиентскому сертификату, PEM. Нужен, только если ваша точка подключения требует взаимного TLS; публичный порт 700 его не требует. |
| `clientKey` | `null` | Путь к вашему закрытому ключу, PEM. Можно не указывать, если ключ вложен в `clientCert`. |
| `clientKeyPassphrase` | `null` | Парольная фраза для зашифрованного клиентского ключа. Неверная — и рукопожатие падает на загрузке ключа, а не на проверке узла. |
| `objUris` | `null` | Объектные сервисы, которые объявлять в `<login>`. `null` означает «ровно то, что предложило приветствие», — поэтому сессию с настройками по умолчанию никогда не отклоняют из-за неподдерживаемого сервиса. Задайте своё значение — и любой URI, который этот сервер не обслуживает, завалит вход кодом 2307. Базовый URI `epp-1.0` никогда не отправляется как объектный сервис, перечислен он в приветствии или нет. |
| `extUris` | `null` | Сервисы расширений, которые объявлять; правило то же. Объявить меньше расширений, чем вы используете, — значит не получить от реестра данные этого расширения. |
| `clTRIDPrefix` | `'PHP-SDK'` | Первый сегмент каждого автоматически создаваемого клиентского идентификатора транзакции. Задайте в нём что-то, по чему ваша система узнаётся в записях реестра. См. [Команды](commands.md#клиентские-идентификаторы-транзакций). |
| `registryExtUri` | `null` | Пространство имён **собственного** объектного расширения этого реестра. `null` — обычный случай — означает «прочитать его из приветствия». Задавайте вручную только для реестра, чьё расширение названо не по образцу `…/registry-<версия>`, по которому идёт определение. Неверное значение не отвергается: расширение в неизвестном серверу пространстве имён ИГНОРИРУЕТСЯ, поэтому данные молча не доходят. См. [Команды](commands.md#собственные-расширения-вашего-реестра). |
| `registryBalanceUri` | `null` | То же самое для расширения баланса учётной записи. |
| `loginSecurity` | `true` | Участвовать в RFC 8807 там, где сервер его предлагает. Значение false лишает вас событий безопасности от сервера. См. [Безопасность входа](#безопасность-входа-rfc-8807). |

### `streamContextOptions(): array`

Возвращает опции потокового контекста PHP, с которыми открывается сокет, в виде `['ssl' => [...]]`.
Полезно, когда рукопожатие не удалось и нужно увидеть, что именно было запрошено:

```php
print_r($config->streamContextOptions());
```

Блок всегда задаёт `verify_peer`, `verify_peer_name`, `SNI_enabled`, `peer_name` (из `host`) и
`crypto_method`, разрешающий **только TLS 1.2 или TLS 1.3**: всё, что старше, отклоняется до того,
как будет записан хоть один байт EPP. `cafile`, `local_cert`, `local_pk` и `passphrase` появляются,
только когда задано соответствующее поле.

## TLS и проверка сертификата
| Сценарий | Настройка |
|---|---|
| `epp.registry.example:700` (сертификат закрытого CA) | укажите в `caFile` файл `.pem` с CA реестра — **обязательно** |
| Публичный сертификат, которому доверяет браузер | значения по умолчанию (`verifyPeer: true`, `verifyPeerName: true`) |
| Несовпадение имени хоста при разработке | `verifyPeerName: false` |
| Точка подключения со взаимным TLS | `clientCert` + `clientKey` (+ `clientKeyPassphrase`, если ключ зашифрован) |

Точка подключения `epp.registry.example:700` предъявляет сертификат, выпущенный **собственным закрытым CA
реестра**. Этого CA нет ни в одном системном хранилище доверия, поэтому `caFile` должен указывать на
его `.pem`-связку. Запросите её у реестра.

В остальном это строгий EPP по RFC, и **клиентский сертификат не нужен**: аутентификация — clID и
пароль поверх TLS плюс белый список IP. Собственные сертификат и ключ нужны, только если ваша точка
подключения требует взаимного TLS.

### Когда рукопожатие не удаётся
Самый частый сбой при первом запуске — проверка сертификата, и выглядит он так:

```
ConnectionException: Cannot connect to epp.registry.example:700 — SSL operation failed …
certificate verify failed
```

Исключение несёт причину, о которой сообщил PHP, а не общее «неизвестная ошибка», поэтому сначала
читайте хвост сообщения. Затем проверьте связку из командной строки:

```bash
openssl s_client -connect epp.registry.example:700 -CAfile /path/to/registry-ca.pem </dev/null
# "Verify return code: 0 (ok)" означает, что связка верна; что угодно другое — что нет.
```

Короткий список диагнозов, в том порядке, в каком их стоит проверять:

| Сообщение | Обычная причина |
|---|---|
| `certificate verify failed` | `caFile` не задан или указывает не на ту связку |
| `did not match expected CN` / несовпадение имени | `host` отличается от имени в сертификате — IP-адрес или псевдоним |
| `Connection refused` / `Connection timed out` | не тот порт либо ваш адрес отправления не внесён в белый список на межсетевом экране |
| сбой при загрузке локального сертификата | неверный путь `clientCert` / `clientKey` или неверная `clientKeyPassphrase` |

**Не хватайтесь за `verifyPeer: false`.** Сообщение исчезнет, а вы останетесь отправлять свой clID,
свой пароль и все коды трансфера тому, кто ответит по этому адресу, — и узнать об этом будет
неоткуда. Если рукопожатие не проходит проверку, значит, связка не та: запросите у реестра
актуальную. `verifyPeerName: false` — более узкое послабление, и при разработке оно иногда оправдано;
`verifyPeer: false` не оправдан нигде.

## Открытие сессии

### `new Client(Config $config, ?Transport $connection = null, ?LoggerInterface $logger = null)`

Создание клиента ничего не открывает. Второй аргумент подменяет транспорт (см.
[Транспорт](#транспорт)); третий подключает логгер PSR-3.

### `connect(): Response`

Открывает TLS-сокет и читает незапрошенное `<greeting>` сервера (RFC 5730 §2.4), возвращая его как
[`Response`](responses.md).

```php
$greeting = $client->connect();
$greeting->serviceObjUris();   // пространства имён объектов, которыми управляет этот сервер
$greeting->serviceExtUris();   // расширения, которые он поддерживает
$greeting->value('svID');      // его имя
$greeting->value('svDate');    // его часы, собственной строкой
```

Две вещи, которых он делать отказывается. Пустой `host` вызывает `ConfigException`. Первый кадр, не
являющийся приветствием, вызывает `ConnectionException`: принять вместо него что пришло значило бы
позволить случайному ответу или баннеру промежуточного узла сойти за перечень сервисов, и тогда вход
объявил бы сервисы, которых этот сервер не предлагает, потеряв при этом расширения, которые он
предлагает.

Вызов `connect()` на уже открытом соединении не переоткрывает сокет — он читает следующий кадр как
приветствие. Для этого используйте `hello()`.

### `greeting(): ?Response`

Последнее прочитанное приветствие или `null` до `connect()`. Помогает решить без обращения к
серверу, доступно ли расширение:

```php
use EppTools\Namespaces;

$fees = in_array(Namespaces::FEE, $client->greeting()?->serviceExtUris() ?? [], true);
```

### `hello(): Response`

Отправляет `<hello>` и читает свежее `<greeting>`, которым отвечает сервер. Два применения:
перечитать меню сервисов и удержать простаивающую сессию — реестр закрывает сессию, которая
простояла слишком долго, а `hello` — самый дешёвый кадр, сбрасывающий этот отсчёт. Возвращённое
приветствие заменяет сохранённое.

### `login(?string $newPassword = null): Response`

Выполняет аутентификацию. Собирает `<login>` с вашими clID и паролем, `<version>1.0</version>`,
настроенным `<lang>` и перечнем сервисов — по умолчанию ровно тем, что предложило приветствие.

```php
$response = $client->login();
$response->code();   // 1000
```

Если вызвать `login()`, не вызвав `connect()`, он сначала подключится.

Проверки, которые выполняются до сборки кадра, каждая — с `ConfigException`:

- пустой `clid` или `password`;
- пароль вне диапазона 6–128 символов;
- пароль длиннее 16 символов, когда этот сервер не объявляет RFC 8807: базовый элемент `<pw>` его не
  унесёт, а сервер ответил бы голым 2001, не назвав ни одного поля.

`AuthenticationException` выбрасывает только код 2200. Вход, отклонённый по любой другой причине,
приходит своим классом со своим способом лечения: 2502 (лимит сессий), 2501 (сервер закрывает
соединение), 2307 (сервис из `<svcs>` не предлагается), 2002 (на этом соединении уже выполнен вход),
2100 (версия протокола). Назвать их все ошибкой аутентификации — значит пойти менять пароль, который
был ни при чём. См. [Ошибки](errors.md).

### `Client::connectAndLogin(Config $config): self`

Статическое сокращение: создаёт клиент, подключается, входит и возвращает готовый клиент.

```php
$client = Client::connectAndLogin($config);
```

Он использует транспорт по умолчанию и не подключает логгер. Если нужно то или другое, пользуйтесь
конструктором.

### `isConnected(): bool` и `isLoggedIn(): bool`

`isConnected()` сообщает, открыт ли сокет. `isLoggedIn()` — удался ли вход и не выполнялись ли с тех
пор `logout()` или `disconnect()`.

Ни один из них не опрашивает сервер, поэтому сессия, которую реестр закрыл сам — по тайм-ауту
простоя, при перезапуске, — может ещё читаться как «вход выполнен», пока не упадёт следующая
команда. Относитесь к ним как к учёту у себя, а не как к проверке живости; проверка живости — это
`hello()`.

## Закрытие сессии

### `logout(): Response`

Отправляет `<logout>`. Сервер отвечает **1500** и закрывает связь. 1500 — код успеха, поэтому
исключения здесь не будет.

### `disconnect(): void`

Закрывает сокет. Его безопасно вызывать, когда ничего не открыто, — поэтому ему место в `finally`:

```php
try {
    $client->connect();
    $client->login();
    // …
    $client->logout();
} finally {
    $client->disconnect();
}
```

Клиент закрывает своё соединение и при уничтожении, проглатывая любую ошибку: исключение из
деструктора подменило бы настоящий сбой вторым. Не полагайтесь на это в долгоживущем процессе:
незакрытая сессия занимает место в вашем лимите одновременных сессий, пока реестр не закроет её по
тайм-ауту.

### `__destruct()`

Клиент закрывает соединение и тогда, когда PHP его уничтожает — в конце запроса или когда исчезает
последняя ссылка на него. Сами вы это не вызываете: это закрытие на крайний случай, последнее.

```php
public function __destruct()
```

Он поглощает любую встреченную ошибку, потому что исключение из деструктора подменило бы настоящую
причину сбоя второй, поднятой в точке, которая о первой ничего не говорит.

Не полагайтесь на него в долгоживущем процессе. Он срабатывает тогда, когда решит PHP, а для воркера,
держащего клиента в статическом свойстве или в контейнере, это может произойти только при завершении
работы — и незакрытая сессия занимает место в вашем лимите одновременных сессий, пока реестр не
закроет её по тайм-ауту. Писать нужно `logout()` по пути наружу и `disconnect()` в `finally`.

Обратите внимание: он закрывает **сокет** и не отправляет `<logout>` — на момент уничтожения кадру
может быть некуда идти. Реестр видит брошенное соединение, а не аккуратное завершение сессии.

## Смена пароля

Передайте новый пароль в `login()` — и он уйдёт как `<newPW>` рядом со старым, в том же кадре
(RFC 5730 §2.9.1.1). Изменение вступает в силу, только если вход удался.

```php
$response = $client->login('N3w-Secret-Pw');
// С этого места сессия аутентифицирована. Каждая СЛЕДУЮЩАЯ сессия должна использовать новый пароль.
```

Порядок здесь важен, потому что спросить у реестра, какой пароль действует, нельзя:

1. **Сначала** запишите новый пароль в своё хранилище секретов, пометив его как ожидающий.
2. Вызовите `login($newPassword)`.
3. При успехе сделайте его действующим. При неудаче действующим остаётся старый: реестр применяет
   изменение только при успешном входе.

Оба пароля проверяются на длину до открытия сокета. 6–16 символов — предел базовой схемы `<pw>`;
6–128 доступны там, где сервер предлагает RFC 8807, а смена **через** эту границу берётся на себя
библиотекой: при замене короткого пароля длинным переносится только новый.

### Длинные пароли
Пароль длиннее 16 символов не может ехать в базовом элементе `<pw>`. Там, где сервер объявляет
RFC 8807, библиотека отправляет в `<pw>` зарезервированный литерал `[LOGIN-SECURITY]`, а настоящий
пароль — в `<loginSec:pw>`; решение о литерале принимается **для каждого элемента отдельно**,
поэтому элемент, который всё ещё несёт собственное значение, никогда не утверждает, что его значение
лежит где-то ещё.

Два следствия, о которых стоит знать до того, как вы такой пароль зададите:

- Длинный пароль проходит аутентификацию только на точке подключения, которая предлагает это
  расширение. Любое ваше ПО, подключающееся к точке, которая его не предлагает, начнёт получать
  отказы в аутентификации.
- Поскольку литерал зарезервирован, `[LOGIN-SECURITY]` сам никогда не может быть паролем.

`Config::$loginSecurity` этим не управляет. Перенесённый пароль отправляет блок в любом случае —
ехать ему больше не в чем.

## Безопасность входа (RFC 8807)
Там, где сервер предлагает расширение безопасности входа, вход несёт небольшой блок,
идентифицирующий этот клиент: имя и версию приложения, версию PHP, семейство ОС, — а сервер отвечает
всем, что хочет видеть исправленным в этой сессии.

```php
foreach ($client->login()->securityEvents() as $event) {
    // type:  certificate | cipher | tlsProtocol | password | newPW | stat | custom
    // level: 'warning' или 'error'
    // text:  фраза, которую можно показать оператору
    alert(
        $event['level'] ?? 'warning',
        $event['type'] ?? 'custom',
        $event['text'],
        $event['exDate'] ?? null
    );
}
```

`securityEvents()` возвращает список ассоциативных массивов. Каждая запись несёт `text`; `type`,
`name`, `level`, `exDate`, `value`, `duration` и `lang` появляются, когда событие их несёт, поэтому
читайте их через `??`. На здоровой сессии список пуст — считайте любую запись поводом действовать.

| `type` | Когда возникает |
|---|---|
| `certificate` | ваш клиентский сертификат скоро истекает; `exDate` содержит точный момент |
| `tlsProtocol` | сессия согласовала устаревшую версию TLS; `name` содержит её |
| `cipher` | сессия согласовала набор шифров, не являющийся AEAD; `name` содержит его |
| `password` / `newPW` | что-то о самих учётных данных — например, длина, ограничивающая места, где их можно использовать |
| `stat` | статистика сессии, которую сервер хочет вам показать |
| `custom` | специфично для сервера; `name` его идентифицирует |

Сервер отправляет их только клиенту, который **участвовал** в расширении, потому что объявление URI
не является свидетельством его поддержки: многие клиенты формируют `<svcExtension>`, просто возвращая
содержимое приветствия. Поэтому блок уходит даже тогда, когда везти в нём нечего.

Поставьте в конфигурации `loginSecurity: false`, чтобы остаться в стороне от расширения. Тогда вы не
получаете событий безопасности, а самое частое из них — клиентский сертификат на подходе к дате
истечения: альтернатива узнать о нём здесь — узнать утром, когда он перестанет работать.

Версия клиента, отправляемая в блоке, — это то, что содержит `Client::VERSION` в установленной вами копии.
Указывайте её в обращении в поддержку.

## Журналирование (PSR-3)

Передайте любой логгер [PSR-3](https://www.php-fig.org/psr/psr-3/) — Monolog, из Laravel, свой
собственный.

```php
$log = new Monolog\Logger('epp');
$log->pushHandler(new Monolog\Handler\StreamHandler('php://stderr', Monolog\Level::Debug));

$client = new Client($config, null, $log);
// или позже; null — отсоединить:
$client->setLogger($log);
```

Что пишется:

| Уровень | Событие |
|---|---|
| `debug` | каждый кадр запроса и каждый кадр ответа, под ключом `frame` |
| `info` | каждый успешный результат — код, `svTRID`, `clTRID` |
| `warning` | каждый неуспешный результат, те же поля |

**Секреты маскируются до того, как кадр попадёт в журнал.** Каждый элемент `<pw>` и `<newPW>`
заменяется на `***` — с любым префиксом пространства имён и любыми атрибутами открывающего тега. Это
покрывает пароль входа, `<newPW>` при смене пароля, `<loginSec:pw>` длинного пароля и `<pw>` внутри
каждого блока `<authInfo>` — то есть код трансфера, единственные учётные данные, позволяющие любому
регистратору забрать у вас домен.

Две вещи, до которых маскирование не дотягивается, потому что это не вывод логгера:

- `Response::raw()` возвращает кадр в том виде, в каком он пришёл, без маскирования. Храните его —
  маскируйте сами.
- Всё, что вы пишете в журнал сами. `authInfo()` возвращает действующие учётные данные: никогда не
  пишите их в журнал, никогда не вкладывайте в обращение в поддержку и меняйте их после того, как
  передали клиенту.

## Транспорт
`Client` общается с внешним миром через интерфейс `EppTools\Transport` — `open()`, `isOpen()`,
`writeFrame(string $xml)`, `readFrame(): string`, `close()`. Реализация по умолчанию,
`EppTools\Connection`, — это TLS-сокет плюс кадрирование по RFC 5734: каждому сообщению предшествует
4-байтовое поле длины в порядке big-endian, **включающее** и сами четыре байта заголовка.

Собственная реализация — это то, чем вы гоняете клиент по записанному обмену в тестах:

```php
$client = new Client($config, new MyRecordedTransport());
```

Два правила, которые соблюдает транспорт по умолчанию и должна соблюдать любая замена:

- Длина кадра меньше 4 байт или больше 1 МиБ отклоняется, а соединение **закрывается**. Байты длины
  к этому моменту уже прочитаны, так что поток стоит на неизвестном смещении.
- Неполное чтение необратимо по той же причине. Продолжив, вы заставили бы следующую команду
  прочитать ответ на текущую — сдвиг на единицу поверх тарифицируемых операций, при котором
  продление возвращает 1000 с датой окончания чужого имени.

Именно поэтому `ConnectionException` посреди команды оставляет результат по-настоящему неизвестным.
Не повторяйте вслепую; см.
[Ошибки](errors.md#когда-трансформирующая-команда-упала-и-вы-не-знаете-выполнилась-ли-она).

## Гигиена сессии

- **По одной команде за раз.** Отправьте команду, прочитайте ответ, затем отправляйте следующую.
  Ради пропускной способности открывайте больше сессий, а не накладывайте команды в одной.
- **Сессии заканчиваются.** От вашего `logout()`, от тайм-аута простоя, от перезапуска на
  обслуживание. Ничто из того, о чём вам уже сообщили, не теряется: прочитанный вами 1000
  окончателен. Переподключитесь и продолжайте.
- **Следите за лимитом одновременных сессий.** 2502 приходит как `SessionException`; лечится он
  закрытием простаивающей сессии, а не немедленным повтором.
